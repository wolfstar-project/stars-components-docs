Changes to [`@wolfstar/http-framework`](https://github.com/wolfstar-project/stars-components/tree/main/packages/http-framework). It provides routing, commands, hot module reloading, and the `stars` CLI for Discord HTTP bots. For the weekly summary across all packages, see the [changelog overview](/documentation/changelog/index).

## `6.2.0`

### New features

- **`stars codegen` command options** — `stars codegen` now generates typed command options from builders. Set `codegen.commands` in `stars.config` (`true`, or `{ output }`, default `src/@types/commands.d.ts`) to make the CLI read commands from the built bot and write a `CommandOptionsRegistry` entry per command path (`'ping'`, `'math add'`, `'subscriptions twitch add'`). The new `Command.OptionsOf<'math add'>` reads it, so a handler no longer needs a hand-written `interface Options` that can drift from the builder: `required` options are not optional, `choices` are a literal union, `channel_types` narrow the channel, and every option has the shape the framework resolves it to. `stars codegen --check` fails with `CODEGEN_OUTDATED` when the file is stale, and `--json` reports it like the i18n generator. ([#275](https://github.com/wolfstar-project/stars-components/pull/275))

### Updates

- **Dependencies** — Updated `@wolfstar/cli` to `2.4.0`, `@wolfstar/schema` to `0.7.0`.

## `6.1.1`

### New features

- **`stars commands diff`, `stars commands deploy`, `stars doctor`, and shell completions** — `stars commands diff` compares the commands the built bot defines with the ones Discord has deployed (`--check` for CI). `stars commands deploy` overwrites them after a confirmation (`--yes` for scripts). The commands are read from the bot itself: it is started with the dev bridge, loads its pieces, reports its registry, and exits before it listens. This needs `@wolfstar/http-framework` 6.1 or later and a built project. `stars doctor` checks the runtime, the framework, the credentials, the dev port, the tunnel, and the generated files, with a fix for each problem (`--online` also asks Discord, `--json` for scripts). `stars completions <bash|zsh|fish>` prints a completion script generated from the registered commands. `stars info` lists the installed modules and the new `dev` options. The `@wolfstar/http-framework` README documents the new `dev` options of `stars.config`. ([#257](https://github.com/wolfstar-project/stars-components/pull/257))

### Updates

- **Dependencies** — Updated `@wolfstar/cli` to `2.3.0`, `@wolfstar/schema` to `0.6.0`.

## `6.1.0`

### New features

- **Vite-style object-based plugins** — Added `definePlugin` and the `StarsPlugin` type (`name`, `enforce: 'pre' | 'post'`, `apply`, and five lifecycle hooks as `(client, options) => ...`), a `plugins` option in `ClientOptions` for per-client plugins, and `PluginHookError`, which attributes a failing hook to its plugin name. `PluginManager` now orders hooks as `pre`, plain, then `post` (registration order inside each group), and `Client.use` accepts plugin objects and nested arrays. The legacy `Plugin` class, symbol hooks, and `registerXHook` keep working through an adapter and emit a one-time `DeprecationWarning` (`HTTP_FRAMEWORK_LEGACY_PLUGIN`) per plugin. ([#246](https://github.com/wolfstar-project/stars-components/pull/246))

### Updates

- **Dependencies** — Updated `@wolfstar/schema` to `0.5.0`, `@wolfstar/cli` to `2.2.0`.

## `6.0.1`

### New features

- **`env` option in `stars.config`** — Added an `env` option that mirrors `@wolfstar/env-utilities`' setup options and is registered automatically as the first import of the built entry, before plugin registrations and the bot's own modules. Added Nuxt-style lifecycle `hooks` (`config:resolved`, `env:options`, `prepare:*`, `builder:created`, `tsdown:options`, `build:*`, `dev:*`) run with `hookable`.
- **`future.compatibilityVersion: 5` by default** — Version 5 is now the default: it is version 4 plus the automatic `env` registration, which turns on when the project depends on `@wolfstar/env-utilities` (and stays off with Nitro). Version 4 is still supported. Version 3 is end-of-life: it still works, now reports a `COMPATIBILITY_VERSION_EOL` warning, and will be removed in the next major. Projects generated by `@wolfstar/create-http-framework` with the `tsdown` or `vite` build no longer call `setup()` from `@wolfstar/env-utilities` by hand; `tsc` and JavaScript projects keep it and set `env: false`. ([#243](https://github.com/wolfstar-project/stars-components/pull/243))

## `6.0.0` (2026-09-24)

### New features

- **`Client.fetch()`** — `client.fetch(request)` is the Web `Request`/`Response` counterpart of `listen()`. It runs the same signature verification and routing without binding a port, for Workers, `Bun.serve`, `Deno.serve`, and similar runtimes.
- **`stars` binary ships with `http-framework`** — Installing `@wolfstar/http-framework` now gives you the `stars` command, with no separate `@wolfstar/cli` install.

### Updates

- **Config schema moved to `@wolfstar/schema`** — The `stars.config.*` schema and loader now live in [`@wolfstar/schema`](/documentation/changelog/stars-components/schema). Imports from `@wolfstar/http-framework/config` keep working unchanged.
- **Plugin support** — [`@wolfstar/plugin-api`](/documentation/changelog/plugins/plugin-api), [`@wolfstar/plugin-i18next`](/documentation/changelog/plugins/plugin-i18next), [`@wolfstar/plugin-logger`](/documentation/changelog/plugins/plugin-logger), and [`@wolfstar/plugin-subcommands-advanced`](/documentation/changelog/plugins/plugin-subcommands-advanced) now target `5.x`.

### Migration

- **Utility decorators moved to `@wolfstar/decorators`** — `ApplyOptions`, `RequiresGuildContext`, `RequiresDMContext`, `RequiresUserPermissions`, `RequiresClientPermissions`, `Enumerable`, `EnumerableMethod`, `createClassDecorator`, `createMethodDecorator`, `createProxy`, `createFunctionPrecondition`, and the `PieceConstructor`/`ContextFallback` types are no longer exported by the framework. Install `@wolfstar/decorators` and import them from there instead; their behaviour is unchanged. The `Register*` decorators and `RestrictGuildIds` stay in the framework. `@wolfstar/decorators` declares `@wolfstar/http-framework` as a peer dependency. `@wolfstar/schema` now includes `@wolfstar/decorators` in its default `imports.presets`, so projects using the `stars` CLI's auto imports keep getting the decorators without an explicit import once the package is installed. ([#238](https://github.com/wolfstar-project/stars-components/pull/238))

## `5.0.0`

### New features

- **`experimental.enableNitro` implemented** — `stars dev`/`stars build` now build the bot through Nitro v3's own Vite plugin (`nitro/vite`, requires Vite 8). `@wolfstar/http-framework`: `Client` now has a `fetch(request, options?)` method, the Web `Request`/`Response` counterpart of `listen()`, running the exact same signature verification, routing, and replies without binding a port, for anything that speaks Fetch instead of `node:http` (Nitro, a Worker, `Bun.serve`, `Deno.serve`, Vite's own dev middleware). The previously-unannounced `@wolfstar/http-framework/fetch` submodule (`createFetchHandler`/`FetchHandler`/`FetchHandlerOptions`) is removed in favour of this method on `Client` itself. `@wolfstar/cli`: `NitroBuilder` reuses the project's own `vite.config.*`/`stars.config#vite`, adds a generated server entry, and produces `.output/` laid out for the configured `experimental.nitro.preset` (`node-server` by default, deployable to anything Nitro targets). `stars dev` rebuilds and restarts on every change. `stars prepare`'s generated `.stars/tsconfig.json` now emits the same `~`/`@`/`~~`/`@@` aliases. ([#207](https://github.com/wolfstar-project/stars-components/pull/207))

### Updates

- **Replace `ConfigError` and `CliError` with `nostics` diagnostics** — `@wolfstar/http-framework/config` no longer exports `ConfigError`/`ConfigErrorOptions`. Every `stars.config.*` validation and load failure is now built from `configDiagnostics` (also exported) and thrown as a `nostics` `Diagnostic`. Catch it with `instanceof Diagnostic` (from `nostics`) instead of `instanceof ConfigError`. The option path is folded into the diagnostic's message; the configuration file is now in `.sources`. `@wolfstar/cli` no longer exports `CliError`/`CliErrorOptions`. Its errors are now built from `cliDiagnostics` and are `Diagnostic` instances too. `formatError` renders a `Diagnostic` with `nostics`' own ANSI formatter; `exitCodeOf` maps `stars.config.*` diagnostic codes to exit code `2` and `BUILD_FAILED` to `3`. `ExitCode`, `exitCodeOf`, and `formatError` keep their existing exports and behaviour for every other case. ([#205](https://github.com/wolfstar-project/stars-components/pull/205))

## `3.6.0`

### New features

- **Aligned `stars dev` terminal UI with Nuxt** — The tsdown builder now leaves dependencies external with `deps.neverBundle`, removing the deprecated option and keeping shared dependencies external for dynamically loaded pieces. Its entry list, target, and output-size table are suppressed; warnings and errors remain available in the log browser and log file. ## `3.5.0`

### New features

- **Configure `tsdown` build from `stars.config`** — The `tsdown` block is now the project's build configuration, typed with the options a bot actually reaches for (`entry`, `format`, `unbundle`, `plugins`, `alias`, `define`, `deps`, `hooks`, ...). What `stars.config` already says fills in the rest, so most projects need nothing in it at all. `build.tsconfig` is now resolved for `tsdown` builds too. `build.configFile` reports which file the build tool is configured from. Two new validation errors: `TSDOWN_OPTIONS_REQUIRE_TSDOWN` and `VITE_OPTIONS_REQUIRE_VITE`. A project that only declares `tsdown: {}` now resolves `build.tool: 'auto'` to `tsdown`. ([#164](https://github.com/wolfstar-project/stars-components/pull/164))
- **Add `future.compatibilityVersion`** — `future` carries the defaults of the next major. `future: { compatibilityVersion: 4 }` changes three things: auto imports are on with the `tsdown` build tool (wired into the build itself); `tsdown` is configured from `stars.config` alone (a `tsdown.config.*` raises `TSDOWN_CONFIG_FILE_UNSUPPORTED`); `build.tool: 'auto'` resolves to `tsdown` for any TypeScript entry without looking for a `tsdown.config.*` or `tsdown` dependency first. `3` is the default and keeps today's behaviour. An unknown version raises `INVALID_COMPATIBILITY_VERSION`. ([#164](https://github.com/wolfstar-project/stars-components/pull/164))

## `3.4.0`

### New features

- **Built-in logger** — `container.logger` is now always available and defaults to a minimal `Logger` that writes to the console, filtered by `LogLevel`. The new `ILogger` interface is the extension point: a plugin can set `options.logger.instance` from a `preGenericsInitialization` hook to replace the built-in implementation, and `new Client({ logger: { level: LogLevel.Debug } })` tunes the default one. The framework internals now log through `container.logger` instead of `console`. ([#159](https://github.com/wolfstar-project/stars-components/pull/159))
- **`stars dev` loop pieces** — Added `dev.typecheck` (runs a type checker next to the bot, supporting `tsc`, `golar`, and `tsz`), `dev.tunnel` (exposes the bot's interactions endpoint publicly via `cloudflared` or a custom URL, with optional `updateEndpoint`), `dev.logFile` (mirrors dev session logs to disk), `stars commands` (lists and cleans deployed application commands), and `stars info` improvements. The interactive `stars dev` UI is now an Ink (React) application. `stars commands clean` without `--name`/`--yes` now runs an interactive wizard. `@wolfstar/cli` requires Node 22 or newer. ([#158](https://github.com/wolfstar-project/stars-components/pull/158))
- **Typed project configuration and the `stars` CLI** — The typed `stars.config.*` schema and loader are owned by `@wolfstar/http-framework` (`@wolfstar/http-framework/config`: `defineConfig`, `loadStarsConfig`, `ConfigError`). `@wolfstar/cli` ships the `stars` binary: `stars dev` builds and restarts the bot, `stars build` runs the build once, `stars info` prints resolved configuration, and `stars codegen` runs i18next type generation. `stars --help` and `stars --version` never load the configuration machinery. ([#158](https://github.com/wolfstar-project/stars-components/pull/158))
- **`experimental` block in `stars.config.*`** — Added `experimental.enableVite` (build through own `vite`), `experimental.enableExternalVite` (watch external build output), and `experimental.enableNitro` (declared but not implemented yet). `stars info` reports which flags are on. ([#158](https://github.com/wolfstar-project/stars-components/pull/158))

## `3.3.0`

### New features

- **`Events` enum** — Every event emitted by `Client` is now available as a member of the `Events` enum, mirroring discord.js' `Events`, so `client.on(Events.CommandError, ...)` can be used instead of the `'commandError'` string literal. Existing string literals keep working. The library now emits through the enum, and the new `ClientEventName` type aliases `keyof ClientEvents`. ([#157](https://github.com/wolfstar-project/stars-components/pull/157))
- **Hot Module Reloading** — `Client` now accepts an `hmr` option that starts a `HotModuleReloader` at the end of `Client#load()`. It watches every path registered in every store and loads, reloads, and unloads pieces in place as their files are created, changed, and deleted, without restarting the process. It accepts all of chokidar's options plus `enabled` (default `true`) and `silent` (default `false`), is exposed as `client.hmr`, and reports operations through new client events (`hmrStart`, `hmrStop`, `hmrPiecesLoaded`, `hmrPieceReloaded`, `hmrPieceUnloaded`, `hmrError`). Unloading a command now also deletes its entry from the `ApplicationCommandRegistry`, so reloading a command no longer leaves the previous entry behind. ([#155](https://github.com/wolfstar-project/stars-components/pull/155))
