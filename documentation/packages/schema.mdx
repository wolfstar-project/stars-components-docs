## Description

`@wolfstar/schema` owns the typed `stars.config.*` schema, the `defineConfig` helper, and the loader that discovers,
validates, and resolves `stars.config.{ts,mts,cts,js,mjs,cjs}`. It sits between
[`@wolfstar/http-framework`](/documentation/packages/http-framework) and
[`@wolfstar/cli`](/documentation/packages/cli), the same way `@nuxt/schema` sits between `nuxt` and `@nuxt/cli`.
Both depend on it, and neither depends on the other.

The package is intentionally side-effect free: importing it from a `stars.config.ts` file never starts a bot or pulls
in the CLI runtime.

## When to use it

Most projects should keep importing `defineConfig` from `@wolfstar/http-framework/config`. The framework re-exports
this package's public surface unchanged, so existing configuration files keep working with no changes needed.

Depend on `@wolfstar/schema` directly when:

- You are building tooling that reads a `stars.config.*` without needing the framework runtime.
- You want the lightweight `@wolfstar/schema/config` entry point in your `stars.config.ts` (just `defineConfig`, no
  loader or diagnostics).

## Usage

The two entry points map to two different needs.

### Configuration files (`@wolfstar/schema/config`)

Use this in a project's `stars.config.ts`. It only exposes the `defineConfig` identity helper and the input types, so
importing it costs nothing at runtime:

```typescript
// stars.config.ts
import { defineConfig } from '@wolfstar/schema/config';

export default defineConfig({});
```

### Tooling and programmatic loading (`@wolfstar/schema`)

The root entry point adds the discovery, validation, and resolution machinery. Use it when a tool needs to load a
project's resolved configuration:

```typescript
import { loadStarsConfig } from '@wolfstar/schema';

const config = await loadStarsConfig({ cwd: process.cwd() });
console.log(config.entry, config.build.output);
```

`loadStarsConfig` discovers the config file, applies the built-in defaults, validates every option, and resolves all
paths to absolute ones. Invalid options raise a diagnostic whose `code`, `path`, `sources`, and `hint` describe the
problem — see [Configuration Errors](/documentation/errors/config) for the full catalog.

For type-only imports of the input and resolved shapes:

```typescript
import type { StarsConfig, ResolvedStarsConfig, BuilderContext } from '@wolfstar/schema';
```

### Default auto imports presets

When a project does not set `imports.presets`, `@wolfstar/schema` resolves it to `@wolfstar/http-framework`,
[`@wolfstar/decorators`](/documentation/packages/decorators), and `@wolfstar/env-utilities`. Auto import generation
skips presets that are not installed in the project. The resolved list is available on
`config.imports.presets`:

```typescript
import { loadStarsConfig } from '@wolfstar/schema';

const config = await loadStarsConfig({ cwd: process.cwd() });
console.log(config.imports.presets);
```

### Dev options

The `dev` block configures `stars dev`. Besides `banner`, `typecheck`, `tunnel`, and `logFile`, it accepts:

| Option                 | Type                                       | Default                              | Description                                                                                                                         |
| ---------------------- | ------------------------------------------ | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `dev.layout`           | `'auto' \| 'dashboard' \| 'panel'`         | `'auto'`                             | The interactive UI. `'auto'` picks the full-screen dashboard on a terminal of at least 90×20 and the compact panel otherwise.       |
| `dev.logs.channels`    | `string[]`                                 | every channel                        | The log channels shown when `stars dev` starts. Other channels start hidden but can still be toggled.                               |
| `dev.logs.levels`      | `StarsLogLevel[]`                          | `['error', 'warn', 'info', 'debug']` | The log levels shown when `stars dev` starts.                                                                                       |
| `dev.logs.dir`         | `string \| false`                          | `false`                              | A directory, relative to `root`, that receives one log file per run (`dev-<timestamp>.log`).                                        |
| `dev.logs.keep`        | `number`                                   | `10`                                 | How many per-run files `dev.logs.dir` keeps, the current run included. Must be a positive integer.                                  |
| `dev.commands.refresh` | `'prompt' \| 'auto' \| 'off'`              | `'prompt'`                           | What `stars dev` does when the bot's application commands change: ask before redeploying, redeploy right away, or only report it. |
| `dev.hmr`              | `boolean`                                  | `true`                               | Leaves changes to pieces to the bot's own hot reload instead of restarting it. `false` always restarts.                             |

```typescript
// stars.config.ts
import { defineConfig } from '@wolfstar/schema/config';

export default defineConfig({
	dev: {
		layout: 'auto',
		logs: { channels: ['bot', 'commands', 'interactions'], levels: ['error', 'warn', 'info'], dir: 'logs', keep: 10 },
		commands: { refresh: 'prompt' },
		hmr: true
	}
});
```

The log file always receives every entry, whatever `dev.logs.channels` and `dev.logs.levels` say. `dev.commands.refresh`
and the bot-side log channels need `@wolfstar/http-framework` 6.1 or later. See
[`stars dev`](/documentation/packages/cli#stars-dev) for how each option behaves.

An unknown value for `dev.layout`, `dev.logs.levels`, or `dev.commands.refresh` raises the
[`INVALID_CHOICE`](/documentation/errors/config#invalid_choice) diagnostic. The package also exports `LOG_LEVELS` (every
level, from the most verbose to the most severe) and `DEFAULT_LOG_LEVELS` (the levels shown by default):

```typescript
import { DEFAULT_LOG_LEVELS, LOG_LEVELS, type StarsLogLevel } from '@wolfstar/schema';
```

## Framework facades

`@wolfstar/http-framework` exposes two facades that forward this package's exports unchanged, matching Nuxt's
package layout:

- `@wolfstar/http-framework/config` — the historical entry point; keep using it in `stars.config.*` files.
- `@wolfstar/http-framework/schema` — the type-focused entry point, mirroring `nuxt/schema`.

Both preserve the same exports and function identities as `@wolfstar/schema`, so existing imports continue to work
without modification.

## Server integration contract

`@wolfstar/schema` exports the `Builder` contract and `BuilderContext` type used by the optional build integrations:

- [`@wolfstar/vite-server`](/documentation/packages/vite-server) — Vite build and dev server.
- [`@wolfstar/nitro-server`](/documentation/packages/nitro-server) — Nitro build and dev server.

Both integrations implement the same lifecycle (`watch`, `close`, `start`/`success`/`failure`/`log` events) so
`@wolfstar/cli` can load them on demand behind the existing experimental flags without depending on either package
at install time.
