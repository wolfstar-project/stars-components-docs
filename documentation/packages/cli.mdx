The typed `stars.config.*` schema and loader live in [`@wolfstar/http-framework`](/documentation/packages/http-framework)
(`@wolfstar/http-framework/config`). This package only consumes it to drive its commands:

- `stars dev` builds the project, starts the bot, restarts it (or leaves the change to the bot's hot reload) and shows what is happening in a full-screen dashboard with filterable log channels and levels (or a compact panel, or plain logs).
- `stars build` runs the configured build tool once.
- `stars info` prints the resolved configuration and environment (`--json` for scripts).
- `stars codegen` runs the configured code generators: i18next types and the typed options of your commands (`--check` for CI).
- `stars prepare` generates `.stars/tsconfig.json` and the auto imports declaration file (`--check` for CI).
- `stars commands` inspects, compares, deploys, and cleans the application commands Discord has deployed.
- `stars doctor` checks that the project is ready: runtime, framework, credentials, interactions endpoint, generated files.
- `stars completions` prints the shell completion script for bash, zsh, or fish.

Everything is driven by a typed `stars.config.ts` file.

## Installation

```sh
pnpm add -D @wolfstar/cli
```

Installing [`@wolfstar/http-framework`](/documentation/packages/http-framework) already gives a project the `stars`
binary. You only need this explicit install to use the package's programmatic exports (`loadStarsConfig`,
diagnostics) or to pin its version independently of the framework's.

Projects scaffolded with [`@wolfstar/create-http-framework`](/documentation/packages/create-http-framework) come with `@wolfstar/cli`, a `stars.config.ts` file and `dev`/`build` scripts already wired up.

## Configuration

`stars.config.{ts,mts,cts,js,mjs,cjs}` is defined by [`@wolfstar/schema`](/documentation/packages/schema) and
re-exported by [`@wolfstar/http-framework`](/documentation/packages/http-framework#project-configuration-starsconfig).
See the framework page for the full option reference (`root`, `entry`, `build`, `dev`, `codegen`) and the
`defineConfig` helper. `stars` looks for the file in the working directory (`--config <file>` overrides it,
`--cwd <dir>` changes the working directory). It passes configuration diagnostics through as exit code `2` and prints
the offending option path and a hint to the terminal.

```ts
// stars.config.ts
import { defineConfig } from '@wolfstar/http-framework/config';

export default defineConfig({});
```

`stars dev`'s URL needs no configuration either — it is detected from `HTTP_PORT` (env var, `src/.env*`/`.env*`, or `dev.env`) or `3000`, the same way Vite's and Nuxt's dev servers do, and `localhost` is swapped for `127.0.0.1` at runtime if that is what is actually reachable. Set `dev.url` only to override it.

The resolved configuration is also available programmatically, exactly as the commands see it (re-exported from this package for convenience, or import it directly from `@wolfstar/http-framework/config`):

```ts
import { loadStarsConfig } from '@wolfstar/cli';

const config = await loadStarsConfig({ cwd: process.cwd() });
console.log(config.entry, config.build.output);
```

## Commands

```sh
stars dev [--no-tui] [--tunnel|--no-tunnel] [--layout <auto|dashboard|panel>] [--channel <name>] [--level <level>] [--theme <name>] [--config <file>] [--cwd <dir>]
stars build [--config <file>] [--cwd <dir>]
stars info [--json] [--config <file>] [--cwd <dir>]
stars codegen [--check] [--json] [--config <file>] [--cwd <dir>]
stars prepare [--check] [--json] [--config <file>] [--cwd <dir>]
stars commands [list|clean|diff|deploy] [--guild <id>] [--name <name>] [--check] [--yes] [--json]
stars doctor [--online] [--json] [--config <file>] [--cwd <dir>]
stars completions <bash|zsh|fish>
stars --help | --version
```

### `stars info`

Prints the resolved configuration and environment. Pass `--json` for scripts. Besides the build, codegen, env, hooks,
and experimental flags, the output lists:

- **Dev**: the `dev` options in effect, including the log file, the per-run log directory and how many files it keeps,
  the layout, the channels and levels the dev UI starts with, the command refresh mode, and whether changes are left to
  the bot's hot reload.
- **Modules**: the installed modules and the runtime plugins they registered.

### `stars dev`

Watches the sources through the configured build tool (`tsdown` programmatically, configured from your `stars.config`, `tsc -b --watch`, or a plain file watcher for JavaScript projects), starts the bot after the first successful build and restarts it after every following one. Failed builds keep the previous process running and wait for the next change; a crashed bot waits for the next change or a manual restart.

The bot runs as a child `node` process with `STARS_DEV=1` and `NODE_ENV=development` in its environment. When the bot
enables the framework's [`hmr` option](/documentation/packages/http-framework#hot-module-reloading), `stars dev` leaves
changes to pieces to the bot instead of restarting it. See [Hot reload](#hot-reload).

`dev.layout` in `stars.config`, or `--layout`, picks the interactive UI:

| Value            | UI                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------- |
| `'auto'` (default) | The dashboard on a terminal of at least 90×20, the panel on a smaller one            |
| `'dashboard'`    | The full-screen dashboard                                                              |
| `'panel'`        | The compact panel pinned to the bottom of the terminal, with the logs folded away      |

Press `v` to switch between the two while a session runs.

`--tunnel` opens the public tunnel at startup for one session, whatever `dev.tunnel` says. When `dev.tunnel` is off,
`stars dev` opens a `cloudflared` quick tunnel. `--no-tunnel` keeps the tunnel closed at startup even when `dev.tunnel`
enables it. Pressing `t` still opens it later. Leave both flags out to let `dev.tunnel` decide. See
[Type checking, tunnel and logs](#type-checking-tunnel-and-logs).

The dashboard is the default on a TTY of at least 90×20. It is a full-screen view in the alternate buffer.

The sidebar shows the state of the session (`starting`, `building`, `running`, `stopped`, `error`), the framework
version, the uptime, the port, the tunnel, and where the logs are written. Below that are the channel and level

The stream prints one line per entry: a level badge (`T D I W E`), the time, the channel, and the message with URLs,
paths, names, and numbers highlighted. An entry with detail lines, such as the commands that were loaded or the paths
that are watched, is shown as a block between two rules. The stack frames the bot prints after an error are folded
under that error and count as one entry. The build percentage follows actual build milestones, not a timer.

#### Log channels

Each log entry has a channel that says what it is about, so you can switch each one off:

| Channel        | What logs there                                                                 |
| -------------- | ------------------------------------------------------------------------------- |
| `cli`          | `stars dev` itself: builds, restarts, hooks, warnings                           |
| `build`        | The build tool and the file watcher                                             |
| `bot`          | Everything the bot writes to stdout and stderr                                  |
| `types`        | The type checker (`dev.typecheck`)                                              |
| `tunnel`       | The public tunnel                                                               |
| `lifecycle`    | The bot is listening, the pieces it loaded                                      |
| `hmr`          | Files left to the bot's hot reload, and what it reloaded                        |
| `commands`     | The application commands the bot registers, changes to them, redeploys          |
| `interactions` | Each interaction: the route (`slash:ping`), the piece, how long it took, errors |
| `http`         | Each request to the interactions endpoint, with its status (`trace` when fine)  |

The last five channels come from the bot itself. `stars dev` preloads a small bridge into the bot (`node --import`)
that reports its events over an IPC channel instead of guessing from stdout. The bridge needs
`@wolfstar/http-framework` 6.1 or later, resolved from the project. Without it, or with a build that bundles the
framework (as Vite and Nitro do), those channels stay empty and everything else works as before.

A plugin can log on a channel of its own:

```ts
process.send?.({ source: 'stars:bridge', type: 'log', channel: 'gateway', level: 'info', text: 'Shard 0 ready' });
```

Entries have one of five levels: `trace`, `debug`, `info`, `warn`, and `error`. `trace` is hidden at start because it
logs one line per request. `dev.logs.channels` and `dev.logs.levels` in `stars.config` choose what a session starts
with. The log file always receives every entry.

```ts
export default defineConfig({
	dev: {
		logs: { channels: ['bot', 'commands', 'interactions'], levels: ['error', 'warn', 'info'] }
	}
});
```

`--channel` and `--level` override them for one session. `--channel` accepts a comma-separated list and can be
repeated. `--level` shows that level and every more severe one.

```sh
stars dev --channel hmr,http --channel commands   # only these channels
stars dev --level trace                           # this level and every more severe one
```

#### Hot reload

When the bot runs with the framework's `hmr` option enabled, it tells `stars dev` which directories it watches. A build
that only changed pieces in those directories is then left to the bot. The process, its HTTP server, and its
connections stay up, and the `hmr` channel shows what was reloaded. A piece is a file the bot loaded one from, or a new
file that could be one.

Any other change still restarts the bot: the entry, a shared module, a locale, or a helper next to the pieces (such as
`_shared.js`, or any file no piece came from), which the bot imports once and cannot replace. A bot without `hmr`, or
one that stopped its reloader, is always restarted. `stars dev` judges what a build changed by content, since a bundler
such as `tsdown` rewrites its whole output on every rebuild.

Set `dev.hmr: false` to always restart the bot:

```ts
export default defineConfig({
	dev: { hmr: false }
});
```

#### Command refresh

The bot reports the application commands it registers when it starts and after every hot reload. When they differ from
what it reported before, `stars dev` reports the change on the `commands` channel. `dev.commands.refresh` picks what
happens next:

| Value               | Behaviour                                                                   |
| ------------------- | --------------------------------------------------------------------------- |
| `'prompt'` (default) | Ask `Refresh commands? (y/n)` in the dev UI and redeploy on `y`            |
| `'auto'`            | Redeploy right away without asking                                          |
| `'off'`             | Only report the change                                                      |

```ts
export default defineConfig({
	dev: { commands: { refresh: 'auto' } }
});
```

Without the interactive UI (`--no-tui`, CI), `'prompt'` only reports the change. An open question survives a restart of
the bot. A `y` given while the bot is stopped or restarting is carried out once it listens again. A refresh also
empties a guild whose last command was removed since the last deploy. Command refresh needs `@wolfstar/http-framework`
6.1 or later.

#### Panel

The panel is used with `dev.layout: 'panel'`, `--layout panel`, the `v` key, or a terminal smaller than 90×20. It is a
bottom-aligned panel in the normal buffer, following the layout and keyboard conventions of
[Nuxt CLI's dev TUI](https://github.com/nuxt/cli/tree/b4b366eafdd9ac4d5b81b6ae7dadda35364252c9/packages/nuxt-cli/src/dev/tui).
It shows a Stars wordmark, aligned URLs, a 20-cell progress bar with elapsed time, status, and shortcuts. Logs are
folded away: `l` opens them and `e` jumps to the last error. Once ready, the bar gives way to diagnostics and the header
reports the load time.

Application output (including its banner), build-plugin output and diagnostics stay in the bounded log history and
`.stars/dev.log`. tsdown's entry list and output-size table are suppressed. Closing an overlay restores the view under
it without duplicating output in scrollback. `running` (`READY` in the panel) reports process state unless
`dev.health` is configured; it does not certify that every application plugin loaded successfully.

In the log browser (`l`): arrows or `j/k` select, `PgUp/PgDn` move a page, `g/G` go to the beginning/follow the tail,
`e/w/a` filter errors/warnings/all, `c/b/r` toggle CLI/build/runtime sources, `/` searches, `x` clears, and
`Enter`/`y` copies the selected line on terminals supporting OSC 52 clipboard writes. `q`, `Esc` or the view's
own shortcut closes an overlay rather than quitting the session.

Replace the default wordmark in `stars.config.ts` (up to four lines are displayed, clipped to the terminal width):

```ts
export default defineConfig({
	dev: { banner: ['★ STARYL', 'Twitch notifications'] }
});
```

`dev.banner` also accepts a string containing newlines, or `false` to hide the wordmark. Omit it for Stars branding.
The dashboard shows the project's name instead of the wordmark. For the application's standalone banner outside the
TUI, use `createStarsBanner` from `@wolfstar/start-banner`.

#### Plain mode

Plain mode prints prefixed lines instead: the channel, then the message, with detail lines indented under it. The bot's
own output is passed through untouched. It is selected by `--no-tui`, `STARS_TUI=plain`, redirected input/output, CI,
`TERM=dumb`, or terminals smaller than 40×10. `STARS_TUI=1` overrides CI/size checks, never redirected streams or a
dumb terminal. Both modes honour `NO_COLOR`/`FORCE_COLOR`; `STARS_REDUCED_MOTION=1` freezes the logo/spinner but keeps
the elapsed clock. Both stop the bot cleanly on `SIGINT`/`SIGTERM`. `SIGUSR2` restarts the bot (not on Windows).

### `stars codegen`

Runs the code generators that `codegen` in `stars.config` enables and writes their files. Pass `--check` in CI to fail
with `CODEGEN_OUTDATED` when a file is stale instead of writing it. Pass `--json` to print `{ check, results }`.

- `codegen.i18n` types the i18next resources with `@wolfstar/i18next-type-generator`. It is on by default when
  `src/locales/en-US` exists.
- `codegen.commands` types the options of every command from its builder. It is off by default. `true` writes
  `src/@types/commands.d.ts`, and `{ output }` picks another file, relative to the project root.

```typescript
import { defineConfig } from '@wolfstar/http-framework/config';

export default defineConfig({
	codegen: { commands: true }
});
```

#### Typed command options

With `codegen.commands` enabled, the generated file augments `CommandOptionsRegistry` with one entry per command path
(`'ping'`, `'math add'`, `'subscriptions twitch add'`):

```typescript
// src/@types/commands.d.ts (generated by `stars codegen`, do not edit)
declare module '@wolfstar/http-framework' {
	interface CommandOptionsRegistry {
		'math add': {
			left: number;
			right: number;
		};
	}
}
```

Handlers type their options with `Command.OptionsOf<'path'>`, so you no longer maintain a hand-written `interface
Options` that can drift from the builder. A renamed option, a flipped `required`, or a changed type stops compiling:

```typescript
public add(interaction: Command.ChatInputInteraction, { left, right }: Command.OptionsOf<'math add'>) {}
```

The generated types follow what the framework resolves at runtime:

- Every option has the shape the handler receives (`user` is `TransformedArguments.User`, `role` is `APIRole`, and so on).
- A `required` option is not optional.
- `choices` become a literal union.
- `channel_types` narrow a channel option.
- A localized command is keyed by its default name, the one the handler receives.
- Context menu commands have no options and are skipped.
- A path registered more than once (a command restricted to several guilds) keeps its first definition.

For an autocomplete handler, `Command.AutocompleteArguments<Command.OptionsOf<'math add'>>` types `focused` from the
same entry.

#### Build first

`stars codegen` reads the commands from the built bot, the same way `stars commands diff` does, so run `stars build`
first. Loops and factories in your builders need no special care, because the types come from what the bot actually
registers. The CLI starts the bot in a mode that loads its pieces, reports its registry, and exits before it listens or
talks to Discord. It never calls `client.login`.

The bot still runs its own setup, so the values it reads while starting (`DISCORD_CLIENT_ID`, `DISCORD_PUBLIC_KEY`, and
so on) must be set. In CI, where the real secrets are not available, pass placeholders:

```sh
stars build
DISCORD_CLIENT_ID=1 DISCORD_TOKEN=x DISCORD_PUBLIC_KEY=0 stars codegen --check
```

Command types are not generated by `stars dev` or `stars prepare`, which has no build to read from yet. Run
`stars codegen` after you change an option, and `stars codegen --check` in CI to keep the file up to date.

### `stars commands`

Lists what Discord currently has deployed, which is not necessarily what the project registers today: renamed and
removed commands stay until something deletes them.

```sh
stars commands list                 # global commands
stars commands list --guild 1234    # a guild's commands
stars commands clean                # wizard: pick from a checklist, then confirm
stars commands clean --name ping    # delete one, asking first
stars commands clean --guild 1234 --yes
```

It reads `DISCORD_TOKEN` and `DISCORD_APPLICATION_ID` (or `APPLICATION_ID`) from the environment or the project's
`.env`, the same place the bot reads them from. `clean` deletes deployed commands, so on a terminal it opens a wizard
(a checklist of what is deployed, then a confirmation). Anywhere else it refuses to run without `--yes` or `--name`.

#### Compare and deploy

`diff` and `deploy` compare what Discord has deployed with what the project defines:

```sh
stars commands diff                 # what a deploy would add (+), change (~) and remove (-)
stars commands diff --check         # the same, failing when anything differs (CI)
stars commands deploy               # show the difference, ask, then overwrite the global scope
stars commands deploy --guild 1234 --yes
```

Commands are declared with builders and decorators that only exist once the bot's modules ran, so `stars` asks the bot.
It starts the built entry with the dev bridge, which loads the pieces, reports the registry, and exits before the bot
listens or talks to Discord. Run `stars build` first. This needs `@wolfstar/http-framework` 6.1 or later.

The bot is started the way `stars dev` starts it (the same env files, after the `env:options` hook), in the caller's
`NODE_ENV`, or `development` when unset. Run `NODE_ENV=production stars commands deploy` to deploy what a production
start registers. `STARS_DEV` is not set, since this is not a dev session.

A command counts as changed when what the project defines no longer matches what is deployed. Fields Discord fills in
on its own (`id`, `version`, defaults such as `nsfw: false`) are ignored. `diff --check` exits with code `1` and raises
`COMMANDS_DIFFER` when anything differs.

`deploy` uses Discord's bulk overwrite, so a deployed command the project no longer defines is deleted. That is why it
asks first. Outside a terminal, or with `--json`, it refuses to run without `--yes`.

### `stars doctor`

Checks what a project needs before `stars dev` can do its job, and says what to do about each problem:

```text
stars doctor v2.3.0
  ✔ node        Node.js v24.19.0
  ✔ config      stars.config.ts
  ✔ framework   @wolfstar/http-framework v6.1.0
  ✔ entry       src/main.ts (tsdown)
  ✖ token       DISCORD_TOKEN is not set
                → Set DISCORD_TOKEN in the environment or in the project .env file.
  ⚠ port        Something already listens on http://localhost:3000
                → Stop it, or set another HTTP_PORT, unless it is this bot running.
  ℹ tunnel      No tunnel: Discord cannot reach a bot on localhost
                → Set `dev.tunnel: true` for a cloudflared quick tunnel, or press t in `stars dev`.
  ⚠ prepare     Out of date: .stars/tsconfig.json
                → Run `stars prepare`.

  1 error(s), 2 warning(s)
```

It covers:

- The Node.js version, and the project's `engines.node`.
- The configuration and its warnings.
- The framework, and whether it is recent enough for the dev bridge.
- The entry and the build output.
- `DISCORD_TOKEN`, `DISCORD_PUBLIC_KEY`, and the application id.
- Whether the dev port is free.
- The tunnel.
- Whether `.stars/` is stale.

`--online` also asks Discord whether the token works and where the application sends its interactions. `stars doctor`
never changes anything. `--json` prints `{ ok, checks }` for scripts. The exit code is `1` when a check fails, with
the `DOCTOR_FAILED` diagnostic.

```sh
stars doctor --online
stars doctor --json
```

### `stars completions`

Prints a shell completion script for bash, zsh, or fish. Add it to your shell's startup file:

```sh
eval "$(stars completions bash)"      # ~/.bashrc
eval "$(stars completions zsh)"       # ~/.zshrc
stars completions fish | source       # ~/.config/fish/config.fish
```

The script is generated from the commands the CLI registers. It completes every command, subcommand, and flag that
`--help` lists, with their short forms (`-c`) and the `--no-` form of flags that are on by default (`--no-tui`).

### Type checking, tunnel and logs

Three `dev` options round out the dev loop (all documented in
[`@wolfstar/http-framework`](/documentation/packages/http-framework#project-configuration-starsconfig)):

- `dev.typecheck: true` runs a type checker next to the bot and reports type errors on the UI's `types` channel,
  without ever blocking a build or a restart. This is useful when building with `tsdown`, which does not type-check.
  `dev.typecheck.checker` picks which one: `tsc` (the project's TypeScript, watch mode), `golar` (`golar tsc`, watch
  mode), `tsz` (the tsc-compatible checker, re-run after every build since it has no watch mode), or `auto`. `auto` is
  the default and uses `golar` when the project depends on it and `tsc` otherwise.
- Pressing `t` opens and closes a `cloudflared` quick tunnel without configuration. `dev.tunnel: true` opens it at
  startup so Discord can reach the bot's interactions endpoint from the internet. `stars dev --tunnel` does the same for
  one session, whatever `dev.tunnel` says, and `--no-tunnel` keeps it closed at startup (`t` still opens it). In plain
  mode (`--no-tui`), where there is no `t` key, the URL is printed on the `tunnel` channel. A string is an https URL you
  already serve, which the CLI only probes. `dev.tunnel.updateEndpoint` writes
  the URL to the Discord application, and is opt-in because it edits a live application.
- `dev.logFile` (default `.stars/dev.log`) mirrors the session's logs to disk, so you can read a run back after the
  terminal UI is gone. Set it to `false` to disable it. The file is truncated on every run.

To keep earlier runs, set `dev.logs.dir` (for example `'logs'`). `stars dev` then also writes one file per run,
`dev-<timestamp>.log`, in that directory. `dev.logs.keep` (default `10`) sets how many per-run files stay, the current
run included. Older files are deleted when a run starts.

```ts
export default defineConfig({
	dev: { logs: { dir: 'logs', keep: 5 } }
});
```

Each line of a log file is `<ISO time> <level> <channel> <message>`, with the detail lines of an entry indented under
it. Log files never filter entries out.

### The build

`tsdown` is configured from `stars.config`, and a base project configures nothing: the entry's directory, one output
file per source file, ESM on Node, `build.outDir`, the tsconfig (`src/tsconfig.json` or `tsconfig.json`), the
extension `build.output` implies, sourcemaps, unbundled dependencies, Nuxt's `~`/`@`/`~~`/`@@` alias prefixes and
the auto imports plugin, and copying `src/locales` to `dist/locales` are all filled in
(the [framework README](/documentation/packages/http-framework#the-build-tsdown) lists every default). The `tsdown` block is for what they
cannot know:

Every `@wolfstar/plugin-*` package listed in the project's `dependencies` or `optionalDependencies` is activated
automatically in bundler builds. `stars` injects its `/register` side-effect entrypoint before the application entry,
so projects do not need to maintain bare imports such as `import '@wolfstar/plugin-i18next/register'`. Packages used
only for development are intentionally not activated from `devDependencies`.

`stars` injects `<name>/register` only when the installed package's `exports` map defines a `./register` subpath.
Library plugins without that entrypoint, such as `@wolfstar/plugin-cache`, `@wolfstar/plugin-gateway`, and
`@wolfstar/plugin-sharder`, are skipped, and you import them directly. A package that is not installed, or that
declares no `exports`, is still injected so a missing install surfaces as a resolution error. If a build fails with
`ERR_PACKAGE_PATH_NOT_EXPORTED` on a library plugin, upgrade to `@wolfstar/cli@2.0.2` or newer, or refresh your
lockfile so it resolves `@wolfstar/vite-server@0.2.2` or newer.

```typescript
export default defineConfig({
	tsdown: { dts: true }
});
```

With `future.compatibilityVersion: 3` an existing `tsdown.config.*` still drives the build and the block is merged
over it (values from `stars.config` win, `plugins` are appended); with `4` the block is the whole configuration. The
`vite` block works the same way for `build.tool: 'vite'`. `stars info` shows which file the build is configured from
and which options the block sets.

### Auto imports

With the `tsdown` build tool, `stars` wires the `autoImports()` plugin into the build, so the exports of every
package in `imports.presets` are usable without an `import` statement. The default presets are
`@wolfstar/http-framework`, [`@wolfstar/decorators`](/documentation/packages/decorators), and
`@wolfstar/env-utilities`. `stars` scans each preset from the project's own `node_modules` and skips packages that are
not installed. Once you add `@wolfstar/decorators` to your dependencies, `ApplyOptions` and the other decorators are
auto-imported.

```typescript
// stars.config.ts
import { defineConfig } from '@wolfstar/http-framework/config';

export default defineConfig({
	imports: {
		presets: ['@wolfstar/http-framework', '@wolfstar/decorators', '@wolfstar/env-utilities']
	}
});
```

Setting `imports.presets` replaces the default list, so keep `@wolfstar/decorators` in it when you customize presets.
`stars prepare` regenerates the auto imports declaration file after you install or remove a preset.

### Compatibility version

`future.compatibilityVersion` selects the legacy or current defaults, the way Nuxt's own compatibility setting does (see the
[framework README](/documentation/packages/http-framework#compatibility-version) for the full reference):

| Version       | What it changes                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------- |
| `3`           | Legacy behaviour: a `tsdown.config.*` drives the build, auto imports off unless asked for                           |
| `4` (default) | `tsdown` configured from `stars.config` alone, auto imports on and wired in, `'auto'` picks `tsdown` for TypeScript |

### Experimental flags

`experimental` in `stars.config.*` turns on work that is still landing (see the
[framework README](/documentation/packages/http-framework#experimental-flags) for the full reference):

| Flag                 | What it changes                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `enableVite`         | Builds through the project's own `vite` (and allows `build.tool: 'vite'`) instead of `tsdown`                             |
| `enableExternalVite` | The project runs Vite itself; `stars dev` only watches the build output and restarts the bot                              |
| `enableNitro`        | Builds through [Nitro](https://nitro.build) (itself a Vite plugin) instead of `node:http`, deployable to any Nitro preset |

`stars info` prints which flags are on.

### Generated TypeScript configuration

The generated compiler options combine `@sapphire/ts-config`, `@sapphire/ts-config/extra-strict`, and
`@sapphire/ts-config/decorators`. The CLI loads these presets and writes their options directly into the file,
so consumers do not need to install Sapphire. This enables strict checks, explicit overrides, and legacy decorators
with metadata. Stars targets ES2022, skips dependency declaration checks, and stores incremental build information
inside `.stars/`. Tsdown and Vite use `ESNext`/`Bundler` with `noEmit`; tsc retains Sapphire's Node16 emit settings.
Project compiler options can override these defaults.

Bundler builds also follow [Nitro's TypeScript configuration](https://github.com/nitrojs/nitro/blob/main/lib/tsconfig.json):
forced module detection, isolated modules, verbatim module syntax, JavaScript sources, `.ts` import extensions,
package.json imports, and ESNext/DOM libraries. Use `import type` and `export type` for type-only dependencies.
These options apply to tsdown and Vite; tsc keeps its emit-compatible settings. Sapphire's decorator options and
the ES2022 target remain in effect. This does not enable Stars' experimental Nitro runtime integration.

Run `stars prepare` and extend the generated config from your project's `tsconfig.json`:

```json
{
	"extends": "./.stars/tsconfig.json"
}
```

New tsdown projects already extend this file and run `stars prepare` through `postinstall`.
Keep your existing compiler options alongside `extends`. `stars dev` and `stars build` also regenerate this file.
For tsdown builds, `@/` and `~/` resolve to the entry file's directory (normally `src/`), while `@@/` and `~~/`
resolve to the project root. Filesystem aliases in `stars.config.ts`'s `tsdown.alias` are included too, with custom
values taking precedence. Legacy builds using a separate tsdown config only include aliases declared in
`stars.config.ts`. Other build tools do not get tsdown aliases, since TypeScript alone does not rewrite imports.

The generated config includes source files and the auto imports declaration, including a custom `imports.dts`
location. Explicit `include` or `compilerOptions.paths` in your own tsconfig replace the inherited values;
remove manually duplicated paths to use the generated aliases. Generation works with `imports: false` too.
Use `stars prepare --check` to check both generated files without writing them. Do not edit `.stars/tsconfig.json`
by hand; keep `.stars/` ignored by Git and run `stars prepare` after installing dependencies on a fresh checkout.

## Server integrations

The Vite and Nitro builders live in dedicated packages —
[`@wolfstar/vite-server`](/documentation/packages/vite-server) and
[`@wolfstar/nitro-server`](/documentation/packages/nitro-server). The CLI loads the selected integration lazily,
passes the resolved `stars.config`, and supplies project dependency loading and plugin registration through
`BuilderContext` from [`@wolfstar/schema`](/documentation/packages/schema). Neither server package depends on the
CLI or framework. Existing experimental flags, presets, output directories, and `stars dev`/`stars build` commands
are unchanged; install Vite and Nitro in the consuming project as before.

See [CLI Errors](/documentation/errors/cli) for every diagnostic code `stars` can raise.
