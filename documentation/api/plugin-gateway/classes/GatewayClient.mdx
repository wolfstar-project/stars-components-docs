A `Client` that, on top of serving HTTP interactions, connects to the Discord gateway, writes every dispatch
into its cache, and emits [GatewayEventMap](/documentation/api/plugin-gateway/interfaces/GatewayEventMap) events carrying structures.

<ApiSignature tokens={['class GatewayClient extends Client']} />

<ApiHierarchy extends={[['Client']]} />

**Example**

```typescript
import { GatewayClient } from '@wolfstar/plugin-gateway';
import { createInMemoryCache } from '@wolfstar/plugin-cache';
import { GatewayIntentBits } from 'discord-api-types/v10';

const client = new GatewayClient({
	intents: GatewayIntentBits.Guilds | GatewayIntentBits.GuildMessages,
	cache: createInMemoryCache()
});

client.on('messageCreate', (message) => console.log(`${message.author.username}: ${message.content}`));

await client.start({ listen: { port: 8080 } });
```

### application

<ApiMember kind="property" badges={['readonly']} signature={['readonly application: ', ['ClientApplication', '/documentation/api/plugin-gateway/classes/ClientApplication']]} source={{ url: 'https://github.com/wolfstar-project/plugins/blob/5bb3b6c632bbc7d73534213f6634e9fd02ee1c15/packages/plugin-gateway/src/GatewayClient.ts#L441', label: 'packages/plugin-gateway/src/GatewayClient.ts:441' }}>

The application of the bot, like discord.js's `Client#application`.

Unlike discord.js, it is never `null`: it is built from [GatewayClientOptions.clientId](/documentation/api/plugin-gateway/interfaces/GatewayClientOptions) when the client is,
so it exists before `READY` and without any gateway connection. It is then partial, see
[ClientApplication.partial](/documentation/api/plugin-gateway/classes/ClientApplication#partial): `READY` patches the same instance with the application's flags, and
[ClientApplication.fetch](/documentation/api/plugin-gateway/classes/ClientApplication#fetch) with the rest. It is kept on the client, not in the cache: it is a single small
object, and every process gets the same `READY`.

</ApiMember>

Runs a hook at the end of every [GatewayClient.destroy](/documentation/api/plugin-gateway/classes/GatewayClient#destroy), see [GatewayClientDestroyHook](/documentation/api/plugin-gateway/type-aliases/GatewayClientDestroyHook).

### reconcileGuilds()

<ApiMember kind="method" badges={['protected']} source={{ url: 'https://github.com/wolfstar-project/plugins/blob/5bb3b6c632bbc7d73534213f6634e9fd02ee1c15/packages/plugin-gateway/src/GatewayClient.ts#L1299', label: 'packages/plugin-gateway/src/GatewayClient.ts:1299' }}>

<ApiSignature
	tokens={[

		['GatewayReadyDispatchData', 'https://discord-api-types.dev/api/discord-api-types-v10#GatewayReadyDispatchData'],
		', shardId: number): ',
		['Promise', 'https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise'],
		'<void>'
	]}
/>

Drops the cached guilds of a shard its `READY` no longer lists, and emits `dispatch` and `guildDelete` for each of
them.

They are the guilds the bot left while it was disconnected, or while the process was down with a persistent
cache. Discord does not replay those removals on a new session, so the cache would otherwise keep them forever.

Each drop is handled as a `GUILD_DELETE` (with `s: 0`) Discord would have sent, `raw` aside: `dispatch` fires once
the guild is gone from the cache, with the cached guild as its state, so forwarding `dispatch` to other processes
(`@wolfstar/plugin-broker`'s `forwardGatewayDispatches`) carries these deletions too.

It needs a guilds cache able to enumerate its entries, and is skipped without one.

It is best effort: any failure (cache unreachable, unknown shard count) is reported through `error` and stops the
reconciliation, keeping the remaining guilds, but never fails `READY` itself.
